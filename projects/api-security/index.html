API Security
Assessment Lab

A reproducible local demonstration of excessive data exposure: compare an over-broad API response with a server-side allowlisted response, then verify the security boundary with automated tests and Burp Suite.

Runnable local lab · 4 automated tests
Source & documentation ↗Assessment template ↗

What was built

Intentionally vulnerable route

/api/v1/profile serializes the full synthetic profile, including internal-only properties.

Remediated route

/api/v2/profile returns only the fields allowed for the profile feature: display name, email, and department.

Automated checks

Tests assert the overexposed fields in the vulnerable response and confirm that the fixed response excludes them.

Burp Suite workflow

Request examples and a step-by-step comparison exercise are included for manual inspection and evidence capture.

Run the lab

python lab/server.py
# In another terminal:
python lab/demo_client.py
# Run tests from repository root:
python -m unittest discover -s projects -p 'test_*.py' -v

Service binds to 127.0.0.1 only and uses synthetic data. The demo identity header is not production authentication.

Scope and evidence

The author has previously reported a crAPI exercise focused on Excessive Data Exposure. The local lab here is a self-contained teaching demonstration, not the crAPI app and not proof of a crAPI finding. Original crAPI endpoint evidence and sanitized captures remain separate items to add from the author's own lab.

Remediation focuses on server-side response schemas, property-level authorization, data minimization, and regression tests.
